Technical Architecture

Target platform · layering · automation model · catalog & pricing · deployment

Salesforce's Revenue Cloud Advanced (RCA / RLM) sits at the centre, with ATS-specific objects layered on top and a strict rule that every cross-object write passes through an Apex domain service. ARCHITECTURE.md §4

🧱 The layered stack — click any layer

⚖️
Governing rule — every cross-object write passes through a domain service. Triggers and Flows never invoke each other. This is what makes the "single source of truth" claim actually true rather than aspirational.

🎯 Platform selection — why Revenue Cloud, not CPQ

🚫
Salesforce CPQ reached end-of-sale in March 2025. Existing customers may renew, but it is no longer sold to new customers and receives no new feature investment. For a greenfield project, installing CPQ today means adopting a frozen product on day one and owning an unavoidable migration later.
DimensionSalesforce CPQRevenue Cloud Advanced
ArchitectureManaged package (SBQQ__*) on top of Sales CloudNative to core Salesforce
Transaction objectsSBQQ__Quote__c etc.Standard Quote, Order, Contract with Transaction Management fields
Quote UISource of truthOne consumer of the API — screens are replaceable
Subscription managementSubscription custom objectAsset-based amendments, renewals, cancellations
Revenue modelsOne-time, term subscription, limited consumptionOne-time, subscription, consumption, hybrid
ComposabilityAll-or-nothing bundleAdopt catalog / pricing / quoting / billing independently
AI readinessLimitedBuilt for Agentforce, APIs, headless

What RCA changes in this design

1 · Asset-based lifecycle
RCA drives amendments, renewals and cancellations from Asset. The provisioned Asset becomes the revenue-managed record; Subscription__c becomes the telecom-specific view layered on it.
2 · API-first pricing
The guided wizard calls the RCA pricing API server-side — it never reimplements pricing in LWC. This eliminates the largest divergence risk between advisor and portal.
3 · Composable adoption
Phases 1–9 need only Product Catalog Management, Salesforce Pricing and Transaction Management. Billing can be deferred pending Q3.

🤖 Automation architecture §7 · "Flow orchestrates; Apex executes"

✅ Use Flow when…
the transaction touches a single object, needs no rollback, and makes no callout.
✅ Use an Apex service when…
the transaction spans ≥2 dependent objects, must be bulk-safe, or makes a callout that must roll back on failure.
🔗 Composition rule
Flow orchestrates; Apex executes. Flows invoke Apex. Never the reverse.

⚡ ActivationService — the critical transaction §7.3

ActivationService.activate(orderId):
  1. Validate     — Order status is Activatable; OrderItems exist; not already activated
  2. For each OrderItem:
       a. Upsert Asset                       (ExternalId = OrderItemId  → idempotent)
       b. Create Subscription__c             (Status = Active, Activation_Date__c = today)
       c. Create Engagement__c               (only if a commitment option is present)
       d. Bind Asset.Contract                (via AssetContractRelationship)
  3. Order.Status = Activated
  4. Create / amend Contract                (if not already created)
  5. Call BSS provisioning                  (callout — 'ON_ERROR_ROLLBACK')
  6. Persist BSS identifiers
  7. Publish Platform Event 'ats.service.activated.v1'   (AFTER commit, not inside)
  8. Schedule Confirmation_Notification

Mandatory properties

IdempotentGuarded by Activation_State__c + unique index on Subscription_Number__c. A double-click must not create two subscriptions.
AtomicSingle Database.save(…, allOrNone: true) with explicit rollback on callout failure. Partial activation is unacceptable.
Bulk-capableA BSS batch may activate 500 orders. Handlers must never assume a single row.
Idempotent calloutSend an idempotency key (Subscription_Number__c) to the BSS.
Outbox patternPlatform event published after commit — consumers never observe phantom state.
ObservableEvery step writes to Integration_Log__c with a shared Correlation_Id__c.

Mandatory state machine §7.4 · enforced by trigger

Draft ──► PendingActivation ──► Active ──► Suspended ──► Active
                                  │
                                  ├──► PendingCancellation ──► Cancelled
                                  └──► Superseded ──► (replacement points here)

Cancelled and Superseded are terminal. Records are never hard-deleted. An explicit allowed-transition map prevents a data load, an integration, or a Flow from moving a record into an illegal state. See the interactive state machine.

Pricing procedure

├── Step 1 — List price          ← PricebookEntry

🧨
Decision tables and procedures must be activated to take effect. An unactivated step silently produces wrong prices with no error.

Client pricing — the architectural rule (X2)

🔐
Neither the wizard nor the portal may compute prices in LWC. All pricing is a server-side call to the RCA Pricing API from CatalogQueryService, returning an authoritative price breakdown. The LWC renders that breakdown read-only. Portal and advisor cannot see different prices, because there is only one pricing implementation.

Try it in the Pricing Lab — the simulator follows the same 5 step procedure.

Phases 1–2 are the critical path. The data model and the catalogue are the two things that are expensive to change later. Everything else is iterative.

The central modelling decision — four lifecycles, not one flat pair. The case study models subscriptions as a flat Subscription__c + Engagement__c pair; this design splits four genuinely-divergent lifecycles: Commercial (Contract), Provisioned (Asset + Entitlement + AssetStatePeriod), Service instance (Subscription__c), Commitment (Engagement__c). Collapsing them is the primary cause of data drift.
