# 02 — Developer Edition constraints and what each one forces

Your stated org reality, and the concrete consequence of each limit.

## 1. The constraint board

| # | Constraint | Consequence | Forced change |
|---|---|---|---|
| 1 | **No Revenue Cloud Advanced** | No pricing procedure, no config rules, no `ProductClassification` | Build Revenue Core (file 03) |
| 2 | **No Experience Cloud licence** | E7 portal cannot exist | Permanently defer E7; keep `UC-ACQ-03` public form as the only customer-facing surface |
| 3 | **No sandboxes** | No UAT/prod separation, no reset button | All testing in the dev org; reset scripts mandatory (`scripts/`) |
| 4 | **5 MB data storage** | Cannot load the real catalogue volume | Test the *pattern*, not the volume — see §3 below |
| 5 | **2 licences** | At most 2 concurrent named users | Profile-based walkthroughs; no parallel team testing |
| 6 | **Not a Dev Hub with scratch allocation** | No disposable orgs, no `sf org create scratch` | Every deploy is to the live org → **backward-compatible deploys only** |

Constraint 6 is the one people underestimate. In the blueprint, E0's exit gate is *"metadata deploys cleanly to an empty org"* — you can never prove that. **Substitute gate:** *metadata deploys cleanly over the current org state, with no errors and no destructive changes.*

## 2. The 2-licence strategy

With two licences, assign them to the two roles that must click through the org daily:

| Licence | Holder | Why |
|---|---|---|
| 1 | P1 (ARCH/DEV/PRICING) | Needs to build and activate pricing, run the advisor wizard |
| 2 | P4 (FRONTEND/ADMIN/OPS) | Needs to build LWC and configure the org |

P2 (DEV/DEVOPS) and P3 (ADMIN/PRICING) work **headlessly**: Salesforce CLI (`sf project deploy start`, `sf data query`, `sf org open --path`), VS Code with the Salesforce extensions, and `sf org login` on a shared session where the licence holder hands over the tab. Everything in the blueprint that is Apex, metadata, LWC source, Flow definition, or a query is doable without a licence seat.

**Rule:** anything that requires clicking Setup or a record page gets batched into a single session owned by the licence holder, and that session becomes a recorded demo artefact (which doubles as portfolio evidence).

## 3. The 5 MB data problem — and the honest answer

E2's exit gate reads *"Committed 5 GB plan prices correctly; 30% device discount fires."* You cannot test 5 GB on 5 MB. Do not pretend otherwise. The defensible engineering answer:

1. **Build the price set programmatically.** `PricebookEntry` rows generated by an Apex test class or an anonymous script from a parameterised seed (`scripts/seed-prices.apex` taking a count).
2. **Test correctness at small scale** — 9 seed products × 3 commitment variants × 2 segments = ~54 entries. That is the real catalogue.
3. **Prove the scaling property without the data.** What could break at 5 GB is *selectivity* and *cardinality*, not correctness. Prove it with:
   - A **query plan / index check** (`EXPLAIN` is unavailable, so use `sf data query` timing on a filtered subset plus a documented index strategy on `Subscription__c.Account__c`, external IDs, and `PricebookEntry` compound keys).
   - A **bulkified unit test** inserting 10 000 `PricebookEntry`-equivalent rows in a loop with `@TestVisible` limits assertions, run at deploy time, never committed as data.
4. **Document the ceiling in the spec**, with the number at which you would move to a real licensed org: *"This pattern is validated to N thousand entries. Beyond that, move to a licensed org with full storage before load."*

That converts a limitation into a documented scaling strategy, which is exactly what `ARCHITECTURE.md` §15/§16 (the empty Performance and Security sections) should contain.

## 4. Testing without sandboxes

| Need | Sandbox answer | Your answer |
|---|---|---|
| Isolated data for a test | Fresh sandbox | `scripts/reset-test-data.apex` — deletes by a `Test_Batch__c` marker field, re-seeds idempotently |
| Rollback of a bad deploy | Re-provision | **You cannot.** → every deploy must be additive-first; destructive changes go through a two-step deploy (add new, backfill, then remove old) |
| UAT | UAT org | The dev org, on a record set tagged `UAT__c = true` |
| Perf test | Full-volume org | §3 above — bulk Apex tests, no data |
| Integration test with a failing endpoint | Mock | `HttpCalloutMock` + a deliberately failing named credential (`UC-INT`'s own requirement) |
| Demo / portfolio snapshot | Full-copy sandbox | Git branch + seed script = reproducible demo state |

**The single most important artefact you must therefore write:** `scripts/reset-test-data.apex`. Without it you have no way to return to a known state, and every manual test makes the org dirtier. Budget it as a Phase 0 deliverable, not an afterthought.

## 5. What you lose permanently

- **E10 Billing** — no RCA Billing SKU, so no invoicing, no revenue recognition. Q3/BQ7 answer from Finance becomes *"external, out of scope"* by default.
- **E7 Portal** — the customer self-service story. `docs/index.html` should show E7 as *deferred — licence required*, not as blocked-and-eventually-built.
- **The `Asset__c` parent-of-truth inversion** (file 01 §3) — you will never have RCA driving amendments, so `Subscription__c` is the truth. This is a **design decision you must record**, not a gap.
- **A realistic "5 GB of prices" demo** — replace with the scaling strategy in §3.

## 6. What you do NOT lose

Everything else in the 80 use cases is buildable on a DE org:

- The six custom objects (`Subscription__c`, `Engagement__c`, `Customer_Request__c`, `Eligibility__c`, `Integration_Log__c`, `Subscription_Wizard_State__c`)
- All 14 standard-object extensions
- All Apex: `LeadImportService`, `OfferBuilderService`, `ActivationService`, `EngagementPenaltyService`, `CatalogQueryService`, the trigger framework
- All LWC: the customer 360° cockpit, the five-step wizard
- All Flows: lead conversion, activation, plan change, cancellation
- Integration: callouts, `Integration_Log__c`, platform events, image sync
- Hardening: FLS/permission sets, IDOR review, translations, the headless CPQ-script test
